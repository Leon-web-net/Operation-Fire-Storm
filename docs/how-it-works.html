How firestorm works

firestorm sits between a sender on port 5733 and a receiver on port 5744. It forwards normal traffic unchanged, takes the CTFS packets out of the stream, and rebuilds the hidden file as 1.pdf. If the run is killed, what it received can still be rebuilt. Step through a run below; each step lights up the part of the program doing the work.

One run, step by step

    
        
    
        
    
          
          
        
    
      
    
    
    
  
    

    


    
  
    The CTFS packet
    
  
    
    
    
      
    16-byte header, then len payload bytes
    
      
    
        
    0C
    1T
    2F
    3S
    
        
    4seq
    5seq
    
        
    6len
    7len
    
        
    8id
    
        
    9sum
    10sum
    11sum
    12sum
    
        
    1300
    1400
    1500
    
      
    
      
    
        markerseq, len (big-endian)file IDchecksum, padding (parsed, not checked yet)
      
    
      
    parse_header() in ctfs.cpp turns these bytes into a CtfsHeader. Packet size = 16 + len. In the test: 20 packets, seqs 0–19, 7 before 6 and 9 before 8, seq 19 has len 0.
    
    
    
    
    
      
    The parser's two states
    
      
    
        
    Searching framing
    Look for CTFS. Forward everything before it. If the read ends in C, CT or CTF, hold just those bytes back: they might be the start of a marker split across two reads.
    
        
    InMessage framing
    Marker found. Wait for 16 header bytes, read len, wait for 16 + len. Hand the packet to on_packet, then go back to Searching. Nothing is stored here.
    
      
    
      
    Bytes that can't be finished yet stay in pending. Usually that's 0–3 bytes, or a packet split across reads.
    
    
    
  
    

    


    
  
    The spool and the index
    
  
    
    
    
      
    Packets arrive as seq 2, 0, 1
    
      
    spool/1.spool on disk, in arrival order. Each record is [seq][len] + payload, flushed to the kernel as soon as it arrives:
    
      
    
        
    2 · 3
    CCC
    0 · 3
    AAA
    1 · 3
    BBB
    
      
    
      
    The index in RAM: a std::map, always ordered by seq.
    
      
    0 → offset 11, len 3
    1 → offset 18, len 3
    2 → offset 4, len 3
    
      
    write_files walks the index 0, 1, 2 and copies one payload at a time to 1.pdf.tmp, giving AAABBBCCC. Then it renames the file to 1.pdf, and only then deletes the spool. Nothing is ever sorted.
    
      
    Crash recovery: each record carries its own seq and length, so if firestorm is killed, ./firestorm --recover reads the spool from the start and rebuilds the index. A torn last record is ignored. The result is named 1.partial.pdf.
    
    
    
    
    
      
    Where the memory goes
    
      
    
        
    WhatWhereSize
    
        
          
    char buf[65536]stack64 KB, fixed
    
          
    pendingheapUsually 0–3 bytes; at most one packet plus one read
    
          
    index (std::map)heapOne small entry per packet
    
          
    payloadsdisk (spool)The whole file, never all in RAM
    
          
    copy buffer in write_filesheapOne payload, at most 64 KB
    
            
      
    
      
    Peak RAM is the index plus one payload, whatever the file size or the packet order. The cost is disk: each byte is written twice (spool, then output) and read back once.
    
    
    
  
    

    


    
  
    When things go wrong
    
  
    
    
    
      
    SituationWhat firestorm doesResult
    
      
        
    Same seq arrives twiceadd_packet keeps the first copy and returns Duplicate; main logs a warningwarn, continue
    
        
    Stream ends partway through a packetfinish() forwards those bytes as normal traffic: they were never a complete packetwarn, continue
    
        
    A gap before the last seq receivedwrite_files warns how many are missing and writes <id>.partial.pdf. Packets missing after the last one received can't be detected.partial.pdf
    
        
    A spool write failsThat spool is marked failed. Traffic keeps flowing to 5744, but the run fails, so no file gets a PDF. All spools are keptexit 1, spools kept
    
        
    recv, connect or send failsLoop stops; finish and write_files are skipped; spools are keptexit 1, spools kept
    
        
    firestorm is killedEvery record already flushed is on disk. --recover rebuilds it as <id>.partial.pdfrecoverable
    
        
    Writing the .tmp file fails.tmp deleted; an older PDF is left untouched; the spool is keptexit 1
    
        
    Clean run, no gapsEach file written via .tmp + rename as <id>.pdf, then its spool is deletedexit 0
